# The Offline Render Was Applying A Realtime Deadline

Status: complete
Created: 2026-08-06
Scope: `signal-plugin-bridge` `shm`, `signal-render-plane` `offline`, and the
`plugin_hosting` load flake this started as

## The Prescribed Fix Was Wrong

The previous note prescribed threading the sandbox lease to twelve call sites
and re-attaching the epoch on retirement, the `A19` fix applied at the point of
use. That was built: a `SandboxBridge` carrying the lease, `ensure_live()` on
every miss, both retry helpers recovering.

Measured under verified load — `18` busy-loop children, `1770%` CPU across `18`
cores, checked before the run: **`6` failures in `6` runs**. Identical to no fix
at all.

Two prescriptions in a row for the same flake, both wrong, is the signal. The
failing samples say why:

```
sample 768:  wet 0.5 vs dry 0.5 * 0.5
sample 128:  wet 0.5 vs dry 0.5 * 0.5
sample 1536: wet 0.5 vs dry 0.5 * 0.5
sample 2048: wet 0.5 vs dry 0.5 * 0.5
```

Different blocks each run, in the middle of the render. Nothing a test helper
does can touch those: `render_plan_to_pcm` drives the processor itself, once per
block, and discards the result — `let _ = processor.process_with_events(..)`.
Retries and re-attaches live in the test harness. The miss was in the product.

## The Defect

`plugin_process_wait_budget` is `min(1 ms, half a block)` — `333 us` at
`32` frames. It is derived from block duration for one reason: a realtime
callback must return before its output buffer drains, so a slow insert is
bypassed rather than waited for. Bypass is correct there. A late block is worse
than an unprocessed one.

`render_plan_to_pcm` runs the same executor, and inherited the same budget.
An offline render has no output buffer. Nothing drains. There, a bypass does not
cost latency — it drops the insert for that block and writes a render that
differs from what the host would play, at a block boundary determined by machine
load rather than by the plan.

So: a user bouncing a mix with a sandboxed plugin insert on a busy machine gets
silent unprocessed blocks scattered through the export. Not reproducible, not
visible, not reported. The test binary had been telling us this since
2026-08-05; it was read as a test flake three times.

## The Fix

`PluginBlockProcessor::set_offline_waiting(bool) -> bool` — offline-driver seam,
defaulting to a no-op, alongside the existing `set_parameter_normalized` seam of
the same shape. `ShmPluginProcessor` swaps its budget for
`PLUGIN_PROCESS_OFFLINE_WAIT_BUDGET` (`5s`) and its spin for a `yield_now`,
since seconds of `spin_loop` would burn a core and starve the child it waits on.

`render_plan_to_pcm` installs `OfflineWaitingGuard` for the render, restoring
each processor's previous setting on drop, including on the `?` early returns.
Restoring matters: a handle is created per live plugin instance and reused, so
latching it would leave the audio thread waiting `5s` on a miss.

`5s` is not a latency target. It only has to exceed a scheduling stall while
still bounding a genuinely dead child at
`PLUGIN_PROCESS_CONSECUTIVE_TIMEOUT_LIMIT` x it.

## Retrying Is Not Idempotent, And The Tests Proved It

With the render fixed, the load run surfaced a different failure — from the
retry helper the bridge work had added:

```
real_child_instrument_accepts_zero_input_and_generates_audio_from_note_events
  assertion failed: scratch[..7 * 2].iter().all(|s| s.abs() < 1e-6)
```

The block carries a `NoteOn` at offset `7`, and samples before it must be
silent. A missed request is still *published*: the parent gave up, the child
served it anyway. The retry then delivered the same `NoteOn` a second time, to a
voice already sounding — so the first samples of the retried block carry the
first attempt's tail.

Retrying a block that carries events is wrong in principle, and this is the
measurement that shows it. Waiting is idempotent; retrying is not.

The whole bridge was therefore reverted. The tests are not audio callbacks
either, so they use the same seam: `process_offline` and
`process_offline_with_events` scope offline waiting across one call. Scoped and
not set at attach, because four tests in that binary assert the *realtime* bound
against a dead child and must keep it.

`SandboxBridge`, `process_with_retries`, and `CHILD_FIRST_RESPONSE_DEADLINE` are
gone.

Full workspace: `89` test binaries green.

## The Tests Were Shown Able To See It

`offline_render_drives_stage_processors_in_offline_waiting` uses a backend that
halves the block only while offline waiting is set, and counts bypasses. With
the guard commented out it fails; with it, it passes. Both directions ran.

`offline_waiting_outlasts_a_stall_the_realtime_budget_bypasses` serves one
request after a `40 ms` stall — `40x` the realtime budget for that block — and
asserts the ratio before relying on it. The first version of that assertion
claimed `120x` and failed, which is the assertion doing its job.

## Note

Three measurements in this thread were worthless for the same reason: `0/8`
where the load never ran, `8/8` idle "failures" that were an artifact of
suppressed output, and `0/10` idle offered as evidence about a load-dependent
failure. The rule stands and keeps being paid for: a measurement must be shown
capable of seeing the thing it claims, and that includes checking the conditions
were applied.
